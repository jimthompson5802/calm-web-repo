# Review: `general-idp-authplugin-design.md`

Findings generated by Codex GPT-5.4 (High)

### High

#### 1. Packaging/build impact of `@finos/calm-auth` is under-specified

The design adds a new `@finos/calm-auth` workspace and a few code touchpoints, but it does not
cover all of the build and packaging surfaces that would need updating in
`architecture-as-code`.

- The root workspace build/test order is hard-coded in places such as `build:cli` and `test:cli`
  in `architecture-as-code/package.json`.
- The CLI build bundles selected internal packages explicitly in `cli/tsup.config.ts`.
- As written, the plan is likely to miss updates needed for `build:cli`, `test:cli`, and published
  CLI packaging.

Relevant references:

- `calm-web-repo/docs/general-idp-authplugin-design.md` sections “Phase 1” and “Files Changed”
- `architecture-as-code/package.json`
- `architecture-as-code/cli/tsup.config.ts`

#### 2. Custom-module support is incomplete for supported CLI installation modes

The design assumes `dynamic import("@acme/...")` plus installing the external package alongside
`@finos/calm-cli`, but the CLI is also documented as installable via Homebrew.

- The review could not find a stated support model for `directUrlAuth.type: custom` when the CLI
  is installed outside npm global/module resolution conventions.
- The design should explicitly state whether `custom` is supported only for npm-based installs, or
  define the supported resolution mechanism for Homebrew users.

Relevant references:

- `calm-web-repo/docs/general-idp-authplugin-design.md` “External Organisation IDP Support” and
  “Constraints and Notes”
- `architecture-as-code/cli/README.md`

### Medium

#### 3. Environment-variable override model is incomplete relative to the proposed config schema

The proposed `directUrlAuth` schema includes more fields than the environment-variable model
actually covers.

The design defines env-var overrides only for:

- `CALM_DIRECT_URL_AUTH_TYPE`
- `CALM_DIRECT_URL_AUTH_TOKEN`
- `CALM_DIRECT_URL_AUTH_CLIENT_ID`
- `CALM_DIRECT_URL_AUTH_CLIENT_SECRET`
- `CALM_DIRECT_URL_AUTH_MODULE`

That leaves these security/deployment-relevant fields impossible to supply via env-only
configuration:

- `apiKey`
- `headerName`
- `tokenUrl`
- `authorizationUrl`
- `redirectPort`
- `scopes`
- `options` for `custom`

Two additional indirection fields are also not expressible via env-only config if that is intended
to be supported:

- `clientSecretEnvVar`
- `envVar` for `static-token`

This matters because several of these values are deployment-specific, and some teams prefer to keep
all runtime configuration out of `~/.calm.json`.

Relevant references:

- `calm-web-repo/docs/general-idp-authplugin-design.md` “Configuration Reference”
- `calm-web-repo/docs/general-idp-authplugin-design.md` “Environment variable overrides for direct URL auth”
- `calm-web-repo/docs/general-idp-authplugin-design.md` implementation step 16

#### 4. User-facing config/update surfaces are missing from the implementation plan

The design focuses on loader and config parsing changes, but it does not include the current
user-facing configuration workflow.

- Today the CLI directs users to `calm init-config` rather than hand-editing `~/.calm.json`.
- The existing `init-config` command only supports `calmHubUrl` and `allowedRemoteHosts`.
- The plan does not include updating `init-config`, CLI help text, or the README/config reference.

That would leave the feature technically present but weakly discoverable and partially undocumented.

Relevant references:

- `architecture-as-code/cli/README.md`
- `architecture-as-code/cli/src/cli.ts`
- `calm-web-repo/docs/general-idp-authplugin-design.md` “Files Changed”

#### 5. The “unchanged CALM Hub auth” description is inconsistent with current code

The design says `authPluginPath` may be a `.js` file or an npm package name, while also claiming
that the existing CALM Hub auth path remains unchanged.

Current implementation behavior does not match that statement:

- `loadAuthPlugin` requires the path to exist on disk.
- `loadAuthPlugin` requires a `.js` extension.
- The module is imported via file URL resolution, not package-name resolution.

So the design currently overstates what the unchanged CALM Hub plugin loader supports.

Relevant references:

- `calm-web-repo/docs/general-idp-authplugin-design.md` “Configuration Reference”
- `architecture-as-code/cli/src/cli-config.ts`

## Open Question

### Scope boundary for `calm-server`

`DirectUrlDocumentLoader` is shared code and is also used by `calm-server`, not only by the CLI.
The design scopes new auth configuration to CLI `~/.calm.json`.

The document should state explicitly whether:

- direct-URL auth is intentionally CLI-only for now, or
- server-side configuration is expected in a follow-up.

Relevant references:

- `architecture-as-code/calm-server/src/index.ts`
- `architecture-as-code/shared/src/document-loader/direct-url-document-loader.ts`
